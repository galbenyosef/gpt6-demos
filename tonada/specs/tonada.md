# Tonada — Composition desk specification

Status: implementation-ready product and technical specification.

## 1. Product definition

Tonada is a browser instrument and composition desk built with HTML, TypeScript, Web Audio, and Three.js. A musician builds a short piece from synthesized and sampled voices, plays it back, and renders it to an audio file, entirely on the local device.

The design thesis is that a composition tool succeeds or fails on its first minute. Within roughly thirty seconds of opening the page, someone with no musical training should have a phrase that sounds deliberate rather than accidental. This is achieved by an **assistance layer** that constrains the editable space to musically coherent choices by default, not by generating music on the user's behalf. The user makes every note decision; the instrument removes the decisions that would only produce mistakes.

Tonada is an instrument, not a digital audio workstation. It has patterns, not a timeline; presets, not a plugin host; a fixed track count, not an arbitrary one. Every sound it makes is produced by code shipped with the application or by audio the user supplies locally.

### Required outcomes

- A project is a versioned document plus a seed. The same document, rendered twice on the same browser build, produces bit-identical audio.
- Offline rendering produces a downloadable audio file faster than realtime, without playing the piece aloud.
- With assistance enabled, no editing action available in the interface can place a note outside the project's key.
- The application ships no recorded audio files. Bundled instrument sounds are generated by code at build time.
- The user can sample their own audio from a microphone or a local file without that audio leaving the device.
- Instrument packs are added as folders of data, with no source change and no registry edit.
- Multiple independent projects can be created, saved, closed, reopened, and continued with their audio state intact.

### Initial scope and defaults

- Desktop browsers with Web Audio, IndexedDB, and Web Locks. Pointer and keyboard input; Web MIDI input is optional and feature-detected.
- Eight tracks, one chord track, one master chain. Patterns up to eight bars, chained into a song of up to sixty-four pattern slots.
- One parametrized synthesis architecture with a subtractive and a two-operator FM mode, plus a sampler player.
- Static hosting, local persistence, and downloadable projects and renders. No account, server, or network dependency at runtime.
- Non-goals for the initial release: multitrack audio recording, a free arrangement timeline, automation curves, custom DSP via `AudioWorklet`, third-party plugin formats, collaborative editing, cloud storage, and touch-first editing.

## 2. Musician experience

### Primary loop

1. Create a project, choosing key, mode, and tempo.
2. Lay a chord progression on the chord track, or accept the generated suggestion.
3. Draw drum and bass parts on the step grid.
4. Draw a melody on the piano roll, where chord tones are marked.
5. Adjust instrument character, track balance, and space.
6. Chain patterns into a song and render it to a file.

The loop must be enterable at any point. A user who only wants to program drums must never be required to touch the chord track, and a user who arrives to sample their own voice must reach the sampler without first composing anything.

### Screens and navigation

**Projects:** Continue for the most recently opened project, New Project, a list of saved projects, and Import Project. Each card shows name, key and mode, tempo, duration, last-modified date, and a static waveform thumbnail of its most recent render if one exists. Card actions are Open, Rename, Duplicate, Export, and Delete. Deletion requires a confirmation naming that project.

**New Project:** accept an optional name, a key and mode, a tempo, a time signature, and an optional seed. Default to C minor, 96 BPM, 4/4, and a fresh random seed. A starter template is selectable and produces a short playable pattern immediately; an empty project is also selectable. Create writes the initial saved state before opening the desk.

**Desk:** the main working surface. A transport bar carries play, stop, loop, tempo, key and mode, the metronome, and the master level meter. The track list shows eight tracks plus the chord track, each with mute, solo, level, and an instrument name. The editor pane shows the step grid for percussive tracks and the piano roll for pitched tracks. The chord track is always visible as a lane beneath the editor so harmonic context is never hidden while editing a melody.

**Instrument:** the editing surface for one track's voice. Parameter groups are ordered by audible impact: character, filter, envelope, motion, effects. Every parameter shows its value in real units, not a raw normalized number. Changes are audible immediately during playback.

**Mixer:** levels, panning, send amounts, and the master chain, with the optional three-dimensional view described in section 6.

**Render:** choose a range (pattern or song), a sample rate, and a bit depth, then render offline with a progress indication and offer the resulting file for download. Rendering never mutates the project.

## 3. Musical model and the assistance layer

### Musical time

Musical position is measured in ticks at 960 pulses per quarter note. Tempo, time signature, and swing convert ticks to seconds. Nothing in the musical model is expressed in seconds, and no scheduling decision consults wall-clock time. A pattern is a bar count, a step resolution, and a set of notes with tick position, tick duration, pitch, and velocity. Step grids are a presentation of the same note data at a coarse resolution, not a separate structure.

Swing is expressed as a percentage displacement of odd subdivisions and is applied at scheduling time from the stored tick positions, so toggling swing never rewrites the document.

### Key, scale, and locking

A project has a tonic and a mode drawn from a documented set: the seven diatonic modes, harmonic and melodic minor, major and minor pentatonic, and blues. With **scale lock** enabled, which is the default:

- The piano roll displays only in-scale pitch rows. Out-of-scale rows are absent, not merely discouraged.
- The musical keyboard maps its keys to successive scale degrees rather than to chromatic semitones.
- Transposition, inversion, and randomization operate within the scale.
- Changing the project key transposes existing notes by scale degree, preserving each note's harmonic function rather than its interval.

Disabling scale lock reveals the full chromatic range and preserves every existing note unchanged. Enabling it again does not delete or move out-of-scale notes already present; those notes remain editable and are marked as outside the current scale. Assistance must never silently destroy the user's material.

### Chord track and progression grammar

The chord track holds one chord per slot, each with a root scale degree, a quality, an optional inversion, and a duration. A progression generator produces candidate progressions from a documented grammar rather than from arbitrary randomness:

- Progressions are built from functional categories — tonic, subdominant, dominant — with permitted transitions per mode.
- Cadence templates close phrases; a generated four-bar or eight-bar progression always ends on a documented cadence.
- Voicings are chosen by a voice-leading pass that minimizes total voice movement between adjacent chords and rejects parallel fifths and octaves between outer voices.
- Generation consumes a dedicated random stream so that regenerating a progression never disturbs humanization or any other seeded behaviour.

The generator is a suggestion mechanism. Every chord it produces is fully editable afterwards, and a progression can be built entirely by hand.

### Melody assistance

While a chord track is present, the piano roll marks each pitch row as a chord tone, a scale tone, or a tension for the chord currently sounding at that horizontal position, using both a colour and a distinct row marker. Marking is advisory: any in-scale note may be placed anywhere.

Two optional transformations assist without composing. **Snap to harmony** moves selected notes to the nearest chord tone. **Fit rhythm** quantizes selected notes to the current step resolution. Both are ordinary undoable edits that rewrite stored note data; neither is a hidden playback-time behaviour.

### Humanization

Humanization applies bounded timing and velocity displacement at scheduling time from a seeded stream, leaving the document unchanged. Timing displacement is drawn from a triangular distribution bounded by a documented tick maximum; velocity displacement is bounded and clamped to the legal velocity range. Humanization is deterministic: the same project, seed, and playback range produce the same displacements every time, including during offline rendering. A humanization amount of zero produces exactly quantized output.

## 4. Sound engine

### Voice architecture

One parametrized voice serves all pitched and percussive synthesis, in two modes.

**Subtractive mode:** two detunable oscillators with selectable waveform, a sub-oscillator, and a noise source, summed and passed through a resonant filter, then a gain stage. **FM mode:** a modulator operator with its own ratio, index, and envelope drives a carrier, then follows the same filter and gain path.

Both modes share an amplitude ADSR, a filter ADSR with a bipolar depth, one LFO routable to pitch, filter cutoff, or amplitude, per-voice detune and pan, and a velocity-to-amplitude and velocity-to-cutoff amount. All parameter changes use scheduled Web Audio parameter automation at explicit times; no parameter is set from a callback firing on the main thread during playback.

Percussion is this same voice with short envelopes and noise-dominant settings, not a separate engine. This keeps one code path under test and makes every drum sound fully editable.

### Polyphony and voice stealing

Each track has a polyphony limit of sixteen voices, with a global ceiling of sixty-four simultaneous voices. When a limit is reached, stealing follows a deterministic policy: the oldest voice already in its release stage is taken first; if none is releasing, the oldest sounding voice is taken. A stolen voice is faded out over a short documented ramp rather than stopped abruptly, to avoid discontinuity clicks. The policy is deterministic so that a rendered file matches what was heard.

Every voice releases its audio nodes when its envelope completes. A project played for an extended period must not accumulate nodes, timers, or scheduled events.

### Sampler

The sampler plays a stored buffer with a root pitch, a playback range, optional loop points, an amplitude envelope, and pitch tracking. It shares the filter, envelope, and effects path with the synthesis voice.

Buffers reach a project by three routes:

1. **Bundled packs**, whose audio is generated at build time by code, as described in section 8.
2. **Microphone capture**, via `getUserMedia`, after an explicit user gesture, with a visible recording state and a documented maximum capture length. Access is requested at the moment of use and never at page load.
3. **Local file import**, decoded with `decodeAudioData`.

Captured and imported audio is stored in the project's IndexedDB record and is never transmitted. Each sample is trimmed, peak-normalized, and stored with its detected root pitch, which the user can correct. A project has documented limits on sample count and total stored sample bytes; reaching a limit produces a clear message and refuses the addition rather than evicting existing samples.

### Track chain, sends, and master

Each track runs a gain stage, a soft saturation stage, a resonant filter, a panner, and two send levels feeding a shared delay and a shared reverb. The delay is tempo-synchronized to a note division with feedback and a damping filter. The reverb is a `ConvolverNode` whose impulse response is **generated**, not loaded: exponentially decaying filtered noise from a seeded stream, with a controllable decay time and pre-delay. Generating the impulse keeps the build free of audio assets and keeps reverb deterministic.

The master chain is a summing gain, a gentle bus compressor, and a final limiter with a documented ceiling below full scale. The limiter is mandatory and cannot be bypassed from the interface: it protects the listener's hearing and guarantees that a rendered file never clips regardless of how the user sets track levels. A DC-blocking high-pass sits before the limiter.

### Gain staging and safety

Audio starts only after a user gesture and is suspended when the document is hidden or focus is lost, resuming on an explicit action. The initial master level is conservative. Rapid parameter changes are ramped rather than stepped, so no interface interaction can produce a discontinuity click. Any parameter capable of self-oscillation, notably filter resonance, is bounded so that no reachable setting produces uncontrolled level growth.

## 5. Timing, scheduling, and determinism

### Reproducibility contract

The same project document, engine version, content version, and render settings produce the same audio buffer, sample for sample, on the same browser build.

- All seeded behaviour — humanization, progression generation, impulse response synthesis, any randomized modulation — draws from explicitly versioned seeded generators with defined integer arithmetic.
- Separate streams are derived for generation, humanization, and sound design so that changing one cannot shift another.
- `Math.random()`, clock time, iteration-order accidents, and frame timing never influence audible output.
- Seeds are normalized with a documented rule: Unicode NFC, trimmed, case preserved; a blank seed requests a fresh one from the cryptographic random API and is then stored verbatim.

This contract is bounded honestly. Web Audio node implementations differ between browsers and between browser versions, so bit-identical output is guaranteed **within** one browser build, not across browsers, and not across engine versions. The project document, not the rendered audio, is the portable artifact. Any comparison test asserting sample equality must state the build it was measured on.

### Scheduler

Playback uses lookahead scheduling against the audio clock. A timer fires at a short documented interval and schedules every event falling inside a schedule-ahead window, using absolute `AudioContext` times. Events are never started from a timer callback at the moment they should sound, and `setTimeout` never determines when a note begins.

The playhead position shown in the interface is derived from `AudioContext.currentTime` and is a display of the audio clock, never a driver of it. Frame rate, window size, and visualization settings must not change what is heard. If the main thread stalls, the already-scheduled window continues to sound correctly and the scheduler resumes without replaying or dropping events at the seam.

Tempo changes take effect at the next unscheduled event boundary, so the already-committed window plays out at its original tempo rather than being retimed mid-flight.

### Offline rendering

Rendering constructs the identical graph in an `OfflineAudioContext` and schedules the entire range at once. The realtime and offline paths share one scheduling implementation; a divergence between them is a defect, not a tolerance. The result is encoded to a WAV file in the browser and offered as a download.

Rendering has a documented maximum duration and reports progress. It must not require playing the piece aloud first, must not depend on any node that only exists in a realtime context, and must produce the same result whether or not the piece has been auditioned in this session.

## 6. Visual design

The three-dimensional layer is optional presentation over an interface that is complete without it. It has two justified uses and must not acquire a third for decoration alone:

**Mixer space.** Each track is an object placed in a room. Horizontal position sets pan and vertical distance sets the send amount to the shared reverb, so spatial placement *is* the mix parameter rather than an illustration of it. Moving an object edits the project.

**Spectrum surface.** A frequency-domain surface driven by an `AnalyserNode` on the master bus, and per-track when a track is focused, making filter sweeps and envelope shapes legible while they are being edited.

Both views are reachable and editable from an equivalent two-dimensional control set. Without WebGL, the application runs with the two-dimensional interface and a clear notice, in the same manner as the collection's other demos. Reduced-motion settings disable continuous animation, and a reduced-flashing setting bounds the spectrum surface's rate of change. Colour is never the sole carrier of meaning in either view.

Visualization reads audio state and never writes it. Analyser polling is bounded, pauses with the transport, and stops entirely when a view is not visible.

## 7. Projects, saving, and loading

### Storage

Use IndexedDB for projects and transactional saves, including sample buffers stored alongside their project. Reserve localStorage for small non-critical preferences such as theme, master level, and the last-opened project. Keep the newest valid revision and one previous valid revision per project; project list metadata and the save revision commit together. A Saved indicator appears only after the transaction commits.

Only one tab may write a project. Use a project-scoped Web Lock; a second tab may list projects but must not silently write the same one.

### Save policy

- Manual save captures the current document and briefly confirms.
- Autosave runs every thirty seconds of active editing, after any structural change such as adding a track or a pattern, after sample import, and before rendering.
- Autosaves are serialized per project and coalesced, so an older snapshot can never overwrite a newer revision.
- If storage fails or reaches quota, keep the session intact, offer retry and export, and never report success.
- Playback state is not save data. A project reopens stopped, at the start of its song, with the transport idle.

### Persisted state

| Group         | Required fields                                                                                     |
| ------------- | --------------------------------------------------------------------------------------------------- |
| Identity      | Project UUID, display name, created / updated / last-opened timestamps                              |
| Compatibility | Document schema version, engine version, content version                                            |
| Musical       | Tonic, mode, tempo, time signature, swing, humanization amount, seed                                |
| Structure     | Tracks, patterns, notes, chord track, song slot order                                               |
| Instruments   | Per-track instrument type, preset reference, and complete parameter values                          |
| Samples       | Sample records with audio data, root pitch, loop points, trim points, and origin                     |
| Mix           | Track levels, pan, send amounts, mute and solo state, master chain settings                          |
| Integrity     | Monotonic revision, payload checksum, previous valid revision reference                              |

A preset reference is stored **together with** its resolved parameter values. A project must reopen and sound correct even if the pack that supplied its preset has been removed, so pack presets are a starting point rather than a runtime dependency.

### Load and compatibility

Read and validate the newest committed revision and its checksum; if it is corrupt, offer the previous valid revision with an explanation. Apply supported migrations to a copy, leaving the source intact until the migrated document commits. Validate versions, finite numeric ranges, identifiers, references, and bounds before constructing any audio node. An unsupported future schema is rejected with a clear message and never overwritten.

### Import and export

Export a self-contained JSON project including document, instrument parameters, embedded samples, metadata, and integrity fields, with a documented maximum file size. Rendered audio is exported separately as WAV and is not part of the project file.

MIDI export produces a Standard MIDI File, type 1, at 960 pulses per quarter note: one track per Tonada track plus the chord track, with tempo and time-signature meta events and track names. MIDI export carries notes and timing only; it is explicitly not a reproduction of the instrument sound, and the interface must say so where the option appears.

Treat every imported project as untrusted structured data. Validate coordinates, ranges, identifiers, sample sizes, and decoded audio dimensions. Render names as text and never evaluate imported content. Import creates a new local project identity, preserving a source identifier for provenance, and can never overwrite an existing project. A malformed, truncated, oversized, or incompatible file leaves stored projects unchanged.

## 8. Packs and extension without code changes

An instrument pack is a folder under `public/packs/<slug>/`, where the slug is lowercase letters, digits, and hyphens. It contains a `pack.json` declaring a bilingual display name, a description, and a list of presets. A preset names its voice mode and its complete parameter set, and a sampler preset additionally names the generator that produces its audio.

Bundled sample audio is never a recorded file. A pack declares sample **generators**: a documented generator identifier plus its parameters, rendered to buffers at build time through an `OfflineAudioContext` and bundled as compact encoded audio. A pack therefore ships as a small readable text file and its generated output, is diffable in review, and is regenerable by rerunning the build.

Complete packs are discovered on each catalog request in development and refreshed before bundling for a static build, matching the deck discovery pattern used elsewhere in this collection. Incomplete or invalid packs are omitted with a build warning rather than failing the build. No registry edit and no source change is required to add a pack.

Interface text is authored in English and Spanish, following the collection's bilingual convention. Both languages are required for any pack-supplied user-visible string.

## 9. Technical structure

Implement as an independent application at `tonada/`, with TypeScript, Web Audio, Three.js, and a Bun development and build workflow, producing static assets. Pin actual dependency versions when implementing.

| Module           | Responsibility                                                                          |
| ---------------- | --------------------------------------------------------------------------------------- |
| `theory.ts`      | Scales, modes, chords, progression grammar, voice leading, chord-tone classification     |
| `document.ts`    | Versioned project types, edit operations, undo history, migrations                       |
| `engine.ts`      | Voice architecture, sampler playback, track chains, sends, master chain                  |
| `scheduler.ts`   | Tick-to-time conversion, lookahead scheduling, humanization, transport state             |
| `render.ts`      | Offline rendering, WAV encoding, MIDI export                                             |
| `packs.ts`       | Pack discovery, validation, sample generators, build-time rendering                      |
| `persistence.ts` | IndexedDB transactions, revisions, locking, import and export                            |
| `validation.ts`  | Bounded schemas and semantic validation for untrusted projects and packs                 |
| `visual.ts`      | Three.js mixer space and spectrum surface, with resource disposal                        |
| `ui/`            | Desk, editors, mixer, dialogs, keyboard access, bilingual strings                        |

`theory.ts` and `document.ts` must contain no audio dependency and must be testable without an audio context. `engine.ts` must not read the project document directly; the scheduler passes it explicit events. Rendering never owns musical state.

Dispose of audio nodes, analysers, GPU resources, event listeners, and timers when switching projects. Repeated project switches must not accumulate resources of any kind.

## 10. Acceptance criteria and verification

### Musical model

- Every mode's scale degrees, chord qualities, and permitted functional transitions match documented references, verified as pure data assertions.
- A generated progression in any supported mode ends on a documented cadence, and its voicings contain no parallel fifths or octaves between outer voices across at least one thousand seeded generations.
- With scale lock enabled, an exhaustive walk of every editing operation exposed by the interface cannot produce an out-of-scale note.
- Enabling scale lock over a chromatic passage preserves every existing note; disabling and re-enabling it is lossless.
- Transposing a project by key moves notes by scale degree and preserves each note's chord-tone classification.

### Audio correctness

- A rendered single note at a known pitch has its measured fundamental within a documented cent tolerance, verified by frequency analysis of the offline buffer.
- A rendered envelope's measured amplitude at the documented attack, decay, sustain, and release checkpoints matches the configured envelope within tolerance.
- A filter sweep's measured spectral centroid moves monotonically with cutoff.
- No rendered output exceeds the limiter ceiling, including a deliberately overloaded project with every track at maximum level and maximum resonance.
- Rendered output contains no NaN or infinite samples and no DC offset beyond a documented threshold.
- Voice stealing under a deliberately over-polyphonic project is deterministic across repeated renders and produces no discontinuity exceeding a documented sample-difference threshold.

### Determinism and timing

- Rendering the same project twice in the same browser build produces bit-identical buffers, including humanization and generated reverb.
- A fixed corpus of at least two hundred seeded projects renders without failure and produces a stable report of per-project audio checksums, duration, and peak level. The report records the browser build it was measured on.
- Rendered note onsets match their scheduled tick positions within a documented sample tolerance across tempo, swing, and time-signature variations.
- Realtime and offline paths produce matching event sequences for the same range, compared as scheduled event lists rather than by ear.
- An induced main-thread stall longer than the schedule-ahead window resumes without duplicated, dropped, or misplaced events.
- Changing visualization settings, window size, or frame rate does not alter a rendered buffer.

### Projects and persistence

- Create projects A and B, make distinct edits in each, reload the browser, and verify both retain their own documents, samples, and mixes.
- Export, clear a test storage profile, import, and continue the same project with identical rendered output.
- Verify corrupt-revision recovery, migration, unsupported-version rejection, duplicate import, quota failure, interrupted transactions, and two tabs opening one project. No case silently overwrites a valid project or falsely reports Saved.
- Removing a pack that supplied a project's preset leaves that project loading and sounding unchanged.
- A project containing the maximum permitted samples exports, imports, and renders within its documented limits.

### Complete application

- A new user can open the page, produce an audible four-bar phrase using only the default project and the assistance layer, and download a rendered file, without documentation.
- Every editing action is reachable by keyboard; grid state is exposed to assistive technology; colour is never the sole cue; reduced-motion and reduced-flashing settings are honoured.
- Audio begins only after a user gesture, suspends on focus loss, and resumes cleanly.
- Microphone access is requested only at the point of use, is clearly indicated while active, and captured audio is verifiably never sent anywhere.
- An extended editing and playback session shows no growth in audio nodes, timers, scheduled events, or GPU resources.

### Human verification, not claimable by automation

Listening quality cannot be asserted by a test suite. The following require a person and must be recorded as outstanding until performed: judging whether the default presets sound good, whether the assistance layer actually shortens the path to a satisfying phrase, whether the mix balances on both speakers and headphones, and whether the limiter's behaviour is transparent at ordinary levels. Automated spectral checks are evidence of correctness, not of musicality.

## 11. Delivery sequence

1. **Sound prototype:** the voice architecture, one track, a lookahead scheduler, and audible playback from a hardcoded pattern.
2. **Musical model:** theory module, scale-locked piano roll and step grid, chord track, project document with undo.
3. **Instrument depth:** FM mode, sampler with microphone and file input, track chain, generated reverb and delay, master limiter, mixer.
4. **Determinism and output:** seeded humanization, offline rendering, WAV encoding, MIDI export, the seeded corpus report.
5. **Projects:** IndexedDB persistence, revisions, locking, import and export, the project browser.
6. **Packs and presentation:** pack discovery, build-time sample generation, bilingual strings, the three-dimensional views, accessibility and comfort settings.
7. **Release verification:** the audio and determinism suites, browser checks, persistence fault cases, and human listening sessions.

The initial release is complete only when a project can be composed with assistance, saved, closed, reopened, rendered to a file that matches what was heard, and exported to another browser profile intact.
