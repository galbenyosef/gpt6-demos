# 001 — Wyang animated parallax wallpaper generator

**Status:** Proposed. **Deliverable:** A Rust desktop demo for macOS and Ubuntu 26.04 LTS running GNOME Shell 50 on Wayland. **Package:** `wyang`.

## 1. The experience

A user drops a daylight photo of a harbor into Wyang and types “Keep the boats and skyline. Make it blue hour, with warm light in the windows.” Wyang sends the image and prompt to an OpenAI image-editing model and displays three alternatives. The user picks one. Moving the pointer across the preview shifts the water in the foreground a little farther than the distant skyline. The boats stay recognizable, desktop icons remain easy to read, and the scene drifts slowly when the pointer rests.

The user can inspect the finished still, see exactly how it will be cropped on their display, pause the movement, and apply the previewed result. They can close the editor and continue using the wallpaper offline. Success means the selected variant, crop, depth and motion survive the trip from the preview to the real desktop.

## 2. One-window editor

| Step | What the user sees and can do | Result |
| --- | --- | --- |
| Import | Drop a PNG, JPEG or WebP, or use **Open image**. | Show the oriented source immediately. Keep its original bytes locally. Explain any decoding or size error and keep the current project open. |
| Describe | Type a prompt, choose 1–4 variations, then press **Generate**. Default to three. Beside the button, identify OpenAI, the image and prompt being sent, and the requested count. | Enable generation when the image, prompt and credential are ready. Show each completed thumbnail, progress such as “2 of 3 ready”, and **Cancel**. |
| Choose | Select a thumbnail beneath the large preview. Hold **View original** to compare at the same display crop. | Each thumbnail is another interpretation of the same source and prompt. Selection updates the preview immediately. Generating another batch adds choices and preserves earlier ones. |
| Preview | Choose a connected display. Toggle **Still / Motion**. Move the pointer over the canvas, or use arrow keys to inspect the extremes. | The canvas shows the selected display's aspect ratio and final crop. A pointer leaving the canvas eases back to rest. An actual-size view allows inspection of the generated pixels. |
| Adjust | Change **Motion strength** or **Ambient drift**. Under **Framing**, drag to reposition the crop. Under **Depth**, adjust the horizon while watching the preview. | Changes are local and immediate. Keep the thumbnail strip and current selection visible. **Reset** restores the selected variant's default settings. |
| Finish | Choose **Save project**, **Export still**, or **Apply to display**. | Save the editable work, write the visible rest pose as a PNG at the target display's pixel dimensions, or start desktop playback. Show which display is active and offer **Stop wallpaper**. |

The main window gives the canvas most of its area. Import and generation sit together, thumbnails sit directly below the canvas, and the apply action stays beside the target display. Make selection, progress and failures readable by keyboard and assistive technology. Switching variants or experimenting with motion changes the draft. The active desktop changes only on **Apply**.

## 3. Source image and OpenAI edits

1. Decode locally, honor EXIF orientation and convert an upload copy to sRGB. Strip metadata from the upload. Enforce a proposed import limit of 32 megapixels and 40 MiB, reject malformed images before allocating full-size buffers, and bound the encoded upload to the selected model's limit. Keep the original file intact.
2. Use multipart `POST /v1/images/edits` with the normalized source in `image`, the user's text in `prompt`, an explicitly configured image model, and PNG output. Start with `gpt-image-2.5-flare`, also configured in the repository's Flip-slop demo. Request one result per call and process the batch sequentially. Each request starts from the same source. This makes individual failures and cancellation visible and prevents a chain of progressively altered compositions. [OpenAI image edits](https://developers.openai.com/api/reference/resources/images/methods/edit) · [Repository configuration](../../flip-slop/example.env)
3. Use a short, recorded prompt suffix asking the model to preserve framing and subject identity unless the user's prompt requests a change. Keep the user's text separately from the effective prompt. Choose a model-supported size closest to the source aspect ratio. The final display crop is a local editor operation. Decode and validate the returned raster before marking a candidate ready. Record its model ID, pixel dimensions, effective prompt and source identity.
4. Read `OPENAI_API_KEY` and the optional `OPENAI_IMAGE_MODEL` from the process environment, filling absent variables from a `.env` in the editor's working directory (`wayang/.env` for a development launch from `wayang/`). Use the model default above when no override is provided. A missing file is valid. If the resolved key is missing or blank, disable **Generate** and identify the variable to set. Only the editor's provider client uses the key. Exclude it from helper process environments, saved projects, logs and packages. Exclude prompts, image bytes and encoded responses from diagnostic logs. Local preview, export and playback work without a credential. Keep the local `.env` ignored by Git and distribute the blank-key [example configuration](../example.env).
5. Disable repeat submission of an active batch. Cancel stops queued work and ignores late results after cancellation. Explain that a submitted request may still incur usage. Retain completed candidates after a partial failure. Distinguish an invalid credential, unavailable model, rejected input, rate limit and network failure. Offer an explicit retry of unfinished slots and show a server-provided retry delay when available. A lost response may already have incurred usage, so retry requires a user action.

The provider creates still artwork. Wyang computes every animation frame on the device. Adjusting a slider, moving the pointer and applying the wallpaper incur zero additional image requests. [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)

## 4. How a single still acquires depth

The first demo uses a **local depth gradient** designed for scenes with a foreground and a horizon. It is deterministic, works on any generated raster, and can be adjusted visually. It approximates scene depth. Tall subjects crossing the horizon can appear to bend, so the editor must let the user reduce strength all the way to zero. The harbor is a suitable first acceptance scene because reflections and distant buildings make excess movement easy to spot.

| Item | Proposed behavior |
| --- | --- |
| Depth field | Use normalized image coordinates after orientation, with vertical coordinate increasing downward. The horizon defaults to 40% of image height. Depth is zero above it and increases smoothly from zero at the horizon to one at the bottom using smoothstep. Store the horizon in image space so changing the display crop preserves its relation to the artwork. |
| Pointer | Normalize the pointer within the target display to the range −1 to +1 on each axis. Ease toward that target with a time constant of about 250 ms. Let other displays settle to center. Preview uses the same normalization inside its canvas. |
| Parallax | At default strength, the nearest pixels move up to 0.5% of the viewport's short edge, about 5 pixels at 1080p. Far pixels stay anchored. Allow up to 1%. Use the depth value to weight the displacement continuously, with motion opposite the pointer. |
| Ambient motion | Add a slow sinusoidal drift with a 24-second period, a default peak of 0.1% of the short edge and a smooth loop. Use the same depth weighting. The strength slider scales both terms, so zero gives a still image. **Ambient drift** can be turned off independently. |
| Framing | Use aspect-fill without stretching. Reserve enough overscan for the maximum combined displacement and filtering on both axes. Constrain the user's focal point to legal crop bounds. Show that crop in both Still and Motion. Portrait, landscape and ultrawide targets use the same rule. |
| Pause and accessibility | A user pause holds the current frame. Still view, zero strength and the system's reduced-motion preference display the centered rest pose. On GNOME, honor the desktop animations setting. Recompute on preference changes and suspend frame production whenever the displayed scene is static. |

Define sampling, timing and crop math in the Rust core. Give the renderer explicit viewport, pointer, elapsed time and motion settings. For fixed inputs it must produce a repeatable frame. This enables a pixel comparison between exported still, GUI preview and the two live hosts.

## 5. Desktop integration

**macOS.** Use Rust with AppKit bindings to create a nonactivating, borderless, click-through window for each applied display. Place it above the system background and below Finder icons using the documented Core Graphics window levels. Read pointer position from AppKit. Keep the window out of the Dock, app switcher and window cycle. Reconcile Spaces, Show Desktop, resolution changes and display reconnection. Closing the editor leaves a menu-bar control with **Open Wyang**, **Pause** and **Stop**. Stopping or quitting removes the surface and reveals the user's existing wallpaper. Apple's desktop-image setter takes a file URL. Live playback belongs to Wyang's running window. [Core Graphics levels](https://developer.apple.com/documentation/coregraphics/cgwindowlevelkey) · [AppKit pointer position](https://developer.apple.com/documentation/appkit/nsevent/mouselocation) · [NSWorkspace](https://developer.apple.com/documentation/appkit/nsworkspace)

**Ubuntu GNOME on Wayland.** Ship a per-user GNOME Shell 50 extension alongside the Rust app. The extension owns placement in Shell's background group, monitor geometry, pointer sampling and suspend/resume signals. Start with one Rust-rendered Wayland surface per active monitor and have the extension display its content in the background group. Match surfaces to the helper launched for the current session. Keep the helper's original windows out of the normal app, task-switcher and overview lists. Prototype surface visibility and compositor throttling early, since a hidden surface may stop receiving frames. The Ubuntu acceptance run must include the default Ubuntu desktop icons and Dock. A working editor preview alone does not establish desktop support. [Ubuntu 26.04 desktop changes](https://documentation.ubuntu.com/release-notes/26.04/changes-since-previous-interim/) · [GNOME 50 extension precedent](https://extensions.gnome.org/extension/11544/wayland-wallpaper-engine/) · [Renderer integration example](https://github.com/BhuwanJoshi-01/wayland-wallpaperengine)

**Linux compatibility.** GNOME's Mutter lacks the optional Wayland layer-shell protocol used by wallpaper clients on compositors such as Sway. The XDG Wallpaper portal sets a background picture. Detect the actual session and extension version before enabling live Apply. On another compositor, or when the extension is missing or disabled, keep editing and PNG export available and identify the missing integration beside Apply. A future layer-shell adapter can consume the same scene. [XDG Wallpaper portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Wallpaper.html) · [GNOME integration rationale](https://github.com/bohdan-mazur/we-wayland-bridge)

**Lifecycle on both hosts.** Apply targets the chosen display. Switching workspaces keeps its wallpaper available. A fullscreen app on that display, screen lock or display sleep suspends its updates. During the GNOME overview, show the system background or the resting scene and resume smoothly on return. Removing a display releases its surface. A helper crash or extension disable must reveal the existing desktop and leave the saved scene available. Replace a running scene only after its successor is decoded and ready. Stop must work with the editor closed.

## 6. Rust implementation and saved work

| Component | Responsibility |
| --- | --- |
| Editor | A Rust desktop GUI, with egui and wgpu as the proposed starting point. Owns image selection, accessible controls, generation jobs, thumbnails, target-display preview and explicit Apply. Decoding, file I/O and HTTP run away from the GUI thread. |
| Provider client | Performs authenticated edits, enforces limits, validates returned bytes and reports each result to its originating batch. Provide a fixture-backed implementation for offline tests. |
| Scene core and renderer | Rust types for variants, crop, depth and motion. Share the same texture sampling and shader between preview, PNG capture and wallpaper playback. Keep native window handles and shell objects outside the scene model. |
| Desktop hosts | AppKit adapter on macOS, Rust player plus a small GJS extension on GNOME. The GNOME bridge carries scene identity, display geometry, normalized pointer and lifecycle events. Load an image once per scene and keep texture data inside the renderer. The existing repo illustrates Rust helper packaging and GNOME version checks. [NotAVirus GNOME protocol](../../not-a-virus/gnome/PROTOCOL.md) |

Use a versioned local project directory containing a JSON manifest, the original image and lossless generated candidates. Reference assets by relative path and content digest. Record variant IDs, generation provenance, selected variant, per-display framing and motion settings. Rebuild the depth field locally from its versioned parameters. Save newly written assets before atomically replacing the manifest. Opening a project after it has moved must work offline. Flag missing or corrupt candidates individually and preserve the rest.

Keep a separate local copy of the last successfully applied scene so moving or deleting an editor project does not break the current desktop. The playback copy needs artwork and scene parameters only. Do not send the image, prompt or key to a telemetry or wallpaper service. Package the macOS app and the Linux editor/player plus matching per-user extension so each can be launched outside the source checkout.

## 7. Delivery order and acceptance

The following are proposed checks. Record automated results separately from observations on a real desktop.

For configuration acceptance, use dummy values with the fixture provider. Exercise an environment-only key, a file-only key, and conflicting values in both places. Confirm the environment wins, a blank key disables generation, and the player starts without inheriting the key. Verify that Git ignores `wayang/.env` and permits tracking `wayang/example.env`.

| Stage | Deliverable and acceptance evidence |
| --- | --- |
| 1. Local preview | Import an oriented portrait photo and a wide harbor fixture. Check both at landscape and portrait display sizes. At centered rest the exported PNG matches the preview crop. Move the pointer from left to right: foreground displacement exceeds skyline displacement, with no gaps or exposed borders at any corner. Zero strength yields identical frames across time and pointer positions. |
| 2. Generation and selection | Use a fixture provider to verify that three jobs carry the same source digest and user prompt, that partial success survives a rate limit, and that cancelling and retrying cannot attach a late result to a different batch. With an authorized live key, produce at least two real edited candidates from one image. Check that both reflect the prompt and retain a recognizable source subject. Reopen the saved project offline and preview either candidate. |
| 3. macOS playback | Apply the harbor variant, close the editor, open a Finder icon, drag-select icons and use the desktop context menu. Exercise Show Desktop, Spaces, lock/unlock and display hot-plug. Confirm the intended display shows the previewed crop, normal clicks and keyboard focus work, and Stop reveals the prior wallpaper. Record macOS version and monitor scale. |
| 4. Ubuntu playback | Repeat on Ubuntu 26.04 with GNOME Shell 50 in a Wayland session, including Activities, fractional scaling, workspace changes and extension disable/re-enable. Verify that no renderer appears in Alt-Tab, no orphan helper survives Stop, and an absent extension produces actionable status while preview still works. Record GNOME version, session type and monitor scale. |
| 5. Motion and resource use | On each host, record a 60-second 1080p run targeting 30 fps, including median and 95th-percentile frame time and CPU use. Target a 95th-percentile render time below 33 ms on the recorded machine. Check frame counters stop during lock, display sleep and reduced motion. Confirm pointer sampling and playback generate no network requests. |

The first demo is complete when one generated scene can be saved, reopened, previewed and applied on both target desktops, and when stopping it restores ordinary desktop behavior. A simulated host can verify scene math and error handling. The two desktop acceptance records establish actual compatibility.
