# H16 architecture

H16 is a word-addressed, 16-bit, five-phase computer. It is intentionally not compatible with Hack, ARM, x86, or any existing instruction set.

## What executes

`H16.stepPhase()` is an explicit control state machine. It fetches/decodes instructions and supplies controls to the circuit-compiled datapath. Arithmetic and bitwise results are **not** computed by a second JavaScript arithmetic emulator: they come from `Simulator` running the NAND netlist of `ALU16`. The `RegisterFile` uses a NAND decoder, two mux trees, and eight registers made from edge-triggered bit cells. PC, SP, and IR use the same `Register16` definition; PC/SP increments use a separate instance of the same ALU. RAM is an explicit word-array storage device. Device writes happen in the MEMORY phase.

The control FSM, instruction decoder, memory array, and external clock are behavioral digital components. They are not claimed to be NAND implementations. NAND is the only combinational primitive; D flip-flops are the sequential primitive, with fixed zero/one sources. A register updates only on a simulated rising edge. All flip-flops in a compiled circuit sample before any update is committed.

The spatial CPU overview is a view of these actual devices and their buses. Hierarchical circuit views come directly from the same `Circuit` definitions that the compiler flattened, and values come from the same indexed signal arrays. There is no post-hoc arithmetic animation.

## Memory map

| Word addresses | Purpose                                 | Permissions                        |
| -------------- | --------------------------------------- | ---------------------------------- |
| `0000–7FFF`    | General RAM and stack                   | Read/write                         |
| `8000–BFFF`    | Program ROM                             | Read; assembler/loader initializes |
| `C000–C3FF`    | 128 × 128 monochrome framebuffer        | Read/write                         |
| `C400–DFFF`    | Reserved / general storage              | Read/write                         |
| `E000`         | Most recent keyboard code               | Read-only device                   |
| `E001`         | Key held: 0 or 1                        | Read-only device                   |
| `E002`         | Completed CPU clock count, modulo 65536 | Read-only device                   |
| `E003–FFFF`    | Reserved / general storage              | Read/write                         |

Words and addresses are 16-bit. Each framebuffer word contains 16 horizontal pixels, most-significant bit on the left. Address of a pixel word: `C000 + y*8 + floor(x/16)`. Bit mask: `8000 >> (x % 16)`. Display rendering reads video memory only; programs never call browser graphics APIs.

The initial PC is `8000`; initial SP is `7FFF`. PUSH writes at SP, then decrements it. POP increments SP, then reads. The stack grows down into RAM. Underflow, overflow, illegal opcodes, and writes to ROM halt the machine with a fault. The stack shares RAM; programs must avoid colliding with their own data.

The display must have keyboard focus to send events. Up/W maps to code 38, Down/S to 40. Blur clears key-held state. This is a single-key device, not a full rollover keyboard.

## Instruction encoding

The first word has the following exact format:

```text
15       11 10      8 7       5 4            0
+----------+---------+---------+--------------+
| opcode   | reg A   | reg B   | reserved = 0 |
+----------+---------+---------+--------------+
```

The opcode is **five bits**. Registers are three bits each (`R0–R7`). Reserved low bits must be zero. Unused register fields are emitted as zero and ignored by the decoder.

`LDI` and all immediate branch/call instructions have a **second 16-bit word**. All other instructions occupy one word. Branch operands are absolute word addresses. The assembler accepts decimal, `0x` hexadecimal, `0b` binary, labels, and signed immediates from -32768 through 65535. Negative values encode as two's complement. There are no hidden relative offsets or byte addresses.

| Opcode | Syntax          | Effect                                 |
| -----: | --------------- | -------------------------------------- |
|      0 | `NOP`           | No operation                           |
|      1 | `HALT`          | Stop execution                         |
|      2 | `MOV Ra, Rb`    | Ra ← Rb through ALU PASS B             |
|      3 | `LDI Ra, imm16` | Ra ← extension word through ALU PASS B |
|      4 | `LD Ra, [Rb]`   | Ra ← memory[Rb]                        |
|      5 | `ST Ra, [Rb]`   | memory[Rb] ← Ra                        |
|      6 | `ADD Ra, Rb`    | Ra ← Ra + Rb                           |
|      7 | `SUB Ra, Rb`    | Ra ← Ra - Rb                           |
|      8 | `INC Ra`        | Ra ← Ra + 1                            |
|      9 | `DEC Ra`        | Ra ← Ra - 1                            |
|     10 | `AND Ra, Rb`    | Ra ← Ra AND Rb                         |
|     11 | `OR Ra, Rb`     | Ra ← Ra OR Rb                          |
|     12 | `XOR Ra, Rb`    | Ra ← Ra XOR Rb                         |
|     13 | `NOT Ra`        | Ra ← NOT Ra                            |
|     14 | `JMP addr16`    | PC ← extension word                    |
|     15 | `JZ addr16`     | Jump if Z = 1                          |
|     16 | `JNZ addr16`    | Jump if Z = 0                          |
|     17 | `JC addr16`     | Jump if C = 1                          |
|     18 | `CALL addr16`   | Push return PC, then jump              |
|     19 | `RET`           | PC ← pop()                             |
|     20 | `PUSH Ra`       | Push Ra                                |
|     21 | `POP Ra`        | Ra ← pop()                             |

The brackets on register-indirect `LD` and `ST` addresses are optional. Labels are case-sensitive; mnemonics/register names are case-insensitive. Semicolon and hash start comments. `.word` emits literal data or resolved label addresses. The assembler uses a token stream, AST, label pass, and encoder, with line/column diagnostics. It reports the first error and emits no partial binary on failure. A failed assembly leaves the loaded machine intact.

## Flags

ADD, SUB, INC, DEC, AND, OR, XOR, NOT update Z/N/C/V. Other instructions preserve them.

- **Z**: result is zero (NAND-derived OR reduction followed by NOT).
- **N**: result bit 15.
- **C**: addition carry-out. For subtraction it means **no borrow** (`A >= B`). Logic operations clear it.
- **V**: signed arithmetic overflow, implemented by XOR of carry into and out of bit 15. Logic operations clear it.

ALU control `OP[2:0]`: 0 ADD, 1 SUB, 2 AND, 3 OR, 4 XOR, 5 NOT A, 6 PASS A, 7 PASS B. SUB inverts B and supplies carry-in 1 to the ripple adder. Result selection uses a three-level 16-bit multiplexer tree.

## Timing and debugger

Every instruction uses five full clocks, including idle phases:

1. **FETCH**: read memory[PC] into IR; increment PC.
2. **DECODE**: decode IR; fetch any extension word and increment PC.
3. **EXECUTE**: select register read paths; propagate the ALU network to stability.
4. **MEMORY**: load/store or stack transfer.
5. **WRITEBACK**: clock destination register/PC, latch flags, finish the instruction.

The instruction-inspector phase tag indicates the **next phase to execute**. The prominent execution panel describes the **last completed phase**, including its actual data transfer, and highlights the corresponding hardware. After stepping EXECUTE, the tag becomes MEMORY and the ALU contains the result, while the destination register retains its old value. One more MEMORY step followed by WRITEBACK commits it. Instruction step runs to the end of the current instruction. Clock and phase step are equivalent in this non-pipelined architecture.

Breakpoints stop before FETCH, so a source breakpoint displays the instruction at PC before executing it. Resume skips that single breakpoint once, permitting progress. Address breakpoints are available in the Memory panel. Continuous scheduling is in the worker, independent of animation or rendering. Clock frequencies are target simulated cycles per wall-clock second; maximum batches work for a bounded time slice and samples visualization. Actual throughput depends on the host.

The trace is a bounded recent-sample buffer, not an unlimited instruction log. Inspectable mode records every CPU phase; fast mode samples once per worker batch. CLK shows sampled alternating clock state, so it is not a physical timing/propagation-delay measurement. Laboratory manual propagation exposes one dependency wave at a time. Its explicit clock step samples all sequential cells atomically.

## Circuit compilation

Circuits have boundary ports, child components, and directed nets. A net has exactly one source and any number of targets. Single-bit references into a bus are explicit adapters (`component.port[bit]`). Each child expands recursively; union/find resolves port aliases; compact signal indices and typed gate arrays replace the editable graph. Kahn's algorithm establishes dependency order and rejects combinational loops. Sequential outputs break feedback dependencies.

Dirty fanout gates are scheduled in a min-heap by topological rank. A gate is queued at most once at a time. Only changed outputs schedule downstream work. NAND implements `0 NAND X = 1`, `1 NAND X = X`; numeric representation is 0/1/2 with 2 representing X. The public model is `0 | 1 | 'X'` and can be extended to a separate Z encoding later.

Supported editor bus widths are 1, 3 (control), 4, 8, and 16. All buses are little-endian indexed internally; integer bit 0 is the least-significant bit. Bus labels show conventional most-significant-digit-first hexadecimal.

## Pong

Pong is a complete assembly source in `src/examples/programs.ts`. RAM words 0–7 hold x, y, dx, dy, left/right paddle y, and scores. The left paddle uses keyboard MMIO. The right paddle follows the ball with bounded movement. A plot subroutine computes video word addresses and uses a ROM mask table to XOR pixels; the same sprites are XOR-erased before moving. Top-row binary indicators encode each score modulo 16. The game has no separate JavaScript update loop.

Choose **Pong**, click **Load**, select **Maximum**, click **Run**, focus the framebuffer, then use ↑/↓. It favors inspectability over game frame rate. Pausing freezes instruction execution and therefore the game.
